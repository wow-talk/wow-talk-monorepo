# ADR 0004 — 슬래시 커맨드를 inspector 트리거로 채택

- **상태**: Accepted
- **날짜**: 2026-05-20

## Context

본 프로젝트의 정체성은 "처음엔 평범한 채팅앱처럼 보이다가, 특정 트리거를 받으면 우측에 read-only WebSocket 터미널이 슬라이드 인하는 이스터에그형 UX"다. 어떤 트리거를 채택할지가 컨셉의 첫인상을 좌우한다.

후보:

1. **슬래시 커맨드** (`/inspect`, `/ws`, `/help` 등) — Discord / Slack / VSCode 명령 팔레트 방식.
2. **콘솔풍 자연어 커맨드** (`sudo show ws`, `enable debug`) — 유닉스 셸 흉내.
3. **키 시퀀스 / 이스터에그** (예: 위·위·아래·아래·좌·우·좌·우, 또는 백틱 3번) — 채팅 입력과 충돌 0인 트리거.
4. **숨겨진 UI 버튼** — 마우스 호버로 표시되는 톱니 아이콘.

## Decision

**슬래시 커맨드** 채택.

핵심 근거:

- **개발자에게 가장 친숙**한 명령 인터페이스. Discord/Slack/VSCode/Notion에서 일상적으로 만나는 문법이라 별도 학습 없이 발견 가능.
- **확장이 자연스럽다**. 새 동작이 필요할 때 `/clear`, `/disconnect` 같이 자유롭게 추가. 키 시퀀스/이스터에그는 추가할수록 발견하기 어려워짐.
- **분기 위치가 명확**. ChatComposer 입력 첫 글자 `/`로 즉시 모드 전환. parser가 한 함수로 끝남.
- **데모 시연에 친화적**. 사용자가 화면 어디를 클릭해야 하는지 추측할 필요 없음. "채팅창에 슬래시 치면 보여요"라는 한 문장 안내로 충분.

## Trade-offs

### 채택안 (슬래시 커맨드)

- 장점:
  - 개발자 친화
  - 확장성 (커맨드 추가 비용 거의 0)
  - 분기 위치 단일 (ChatComposer)
- 단점:
  - 일반 메시지를 `/`로 시작하고 싶을 때 충돌 — v0에서는 모든 `/` 시작을 커맨드로 다룸. escape 규약은 추후.

### 미채택 1 — 콘솔풍 자연어

- 장점: "탈옥/해킹" 분위기 강함
- 단점: 자연어 파싱 모호함 (`sudo show ws` vs `sudo show all`), 모르는 문법으로 잘못 입력하면 자기 의도가 명확치 않음

### 미채택 2 — 키 시퀀스

- 장점: 채팅 입력과 충돌 0
- 단점: 발견 불가능에 가까움. 데모 시연 때 "이걸 어떻게 알아요?" 가 첫 질문이 됨

### 미채택 3 — 숨겨진 UI 버튼

- 장점: 마우스 한 번으로 해결
- 단점: "처음엔 평범한 채팅앱"이라는 컨셉의 정수가 사라짐. UI에 보이면 평범한 토글 버튼.

## Consequences

긍정적:
- v0 사전 정의 5개(`/inspect`, `/ws`, `/clear`, `/disconnect`, `/help`)로 데모 흐름 완결.
- inspector를 토글하는 동작이 다른 커맨드(예: `/clear`, `/disconnect`)와 같은 인프라(parser + registry + handlers) 위에 얹힘 → 코드 중복 없음.
- 새 동작 추가 시 핸들러 하나만 작성 + registry에 한 줄 등록.

부정적 / 비용:
- `/`로 시작하는 일반 메시지를 보낼 수 없음. 필요할 때 escape 규약(예: `\/` 또는 `>` 시작) 결정 필요.
- 모바일에서 슬래시 입력이 키보드 깊이 들어가 있어 trigger discoverability 가 약간 떨어짐. 추후 placeholder/플로팅 hint로 보강 가능.

후속 작업 후보:
- 커맨드 자동완성 드롭다운(`/`만 쳐도 후보 5개 표시)
- escape 규약 결정 (`/`로 시작하는 일반 텍스트 메시지)
- ADR-0005: WS 재연결 정책 (별도)
